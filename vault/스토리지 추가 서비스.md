# 스토리지 추가 서비스

> S3·EBS 외의 스토리지 — 대용량 이전(Snow), 파일 시스템(FSx), 하이브리드(Storage Gateway).

## 개요

S3·EBS·EFS 말고도 AWS에는 특정 상황을 겨냥한 스토리지 서비스가 여럿 있다. 시험은 "이 시나리오엔 어느 서비스?"를 묻는다. 큰 분류:

- **데이터 이전** — 오프라인 물리 장치(Snow Family) vs 온라인 네트워크 동기화(DataSync).
- **관리형 파일 시스템** — 고성능·서드파티 파일 시스템(FSx 4종).
- **하이브리드(온프레미스 ↔ 클라우드)** — Storage Gateway 3종.
- **파일 전송 인터페이스** — FTP 계열로 S3/EFS에 접근(Transfer Family).

## 설계 관점 (SAA) #saa

![[AWS Certified Solutions Architect Slides v47.pdf#page=350]]

### Snow Family (오프라인 대량 이전)

물리 장치를 받아 데이터를 담아 다시 AWS로 보내는 **오프라인** 이전·엣지 컴퓨팅 도구. **네트워크로 전송하는 데 일주일 넘게 걸리면 Snowball을 쓴다**는 게 판단 기준.

- **Snowball Edge** — 페타바이트급 이전. **Storage Optimized**(스토리지 위주, 210TB)와 **Compute Optimized**(연산 위주, 28TB).
- **Edge Computing** — 인터넷이 약하거나 없는 현장(트럭·선박·광산)에서 Snowball Edge로 EC2·Lambda를 돌려 데이터를 전처리·ML·트랜스코딩.
- **Glacier로 직접 못 넣는다.** Snowball → **S3** → S3 라이프사이클 정책으로 Glacier 이동.

### Amazon FSx (관리형 파일 시스템 4종)

서드파티 고성능 파일 시스템을 관리형으로 제공. 어떤 워크로드냐로 고른다.

- **FSx for Windows File Server** — 관리형 **Windows** 파일 공유. **SMB·NTFS**, Active Directory·ACL·사용자 쿼터. **Linux EC2에도 마운트 가능**, DFS Namespaces 지원. 온프레미스에서 VPN/DX로 접근, Multi-AZ 구성 가능, S3로 매일 백업.
- **FSx for Lustre** — **HPC·머신러닝** 같은 대규모 병렬 연산용(이름은 Linux+cluster). 수백 GB/s·sub-ms 지연. **S3와 긴밀 통합**(S3를 파일 시스템처럼 읽고 결과를 S3에 씀). 배포 옵션: **Scratch**(임시, 복제 안 함, 고버스트, 단기 처리·비용 절감) vs **Persistent**(장기, 같은 AZ 내 복제, 장애 파일 수 분 내 복구, 민감·장기 데이터).
- **FSx for NetApp ONTAP** — **NFS·SMB·iSCSI** 모두 호환. ONTAP/NAS 워크로드를 옮길 때. 스토리지 자동 증감, 스냅샷·복제·압축·중복 제거, 즉시 복제(클로닝).
- **FSx for OpenZFS** — 관리형 **OpenZFS(NFS)**. ZFS 워크로드 이전용, 최대 100만 IOPS·0.5ms 미만, 스냅샷·압축·즉시 클로닝.

### Storage Gateway (하이브리드)

온프레미스와 클라우드 스토리지를 잇는 다리. 재해 복구·백업·계층형 스토리지·온프레미스 캐시에 쓴다. S3는 EFS/NFS와 달리 독자 기술이라 온프레미스에 그대로 노출할 수 없는데, 이를 Storage Gateway가 해결한다. 세 종류:

- **S3 File Gateway** — S3 버킷을 **NFS·SMB**로 접근. 최근 쓴 데이터는 게이트웨이에 캐시. S3 Standard·IA·One Zone-IA·Intelligent-Tiering 지원, 라이프사이클로 Glacier 이동. 버킷 접근은 IAM 역할, SMB는 AD 인증.
- **Volume Gateway** — **iSCSI 블록 스토리지**(S3 백업, EBS 스냅샷으로 온프레미스 볼륨 복구 가능). **Cached volumes**(최근 데이터만 로컬 캐시) vs **Stored volumes**(전체 데이터가 온프레미스, S3로 예약 백업).
- **Tape Gateway** — 기존 테이프 백업 절차를 클라우드로. S3·Glacier 기반 가상 테이프 라이브러리(VTL), iSCSI 인터페이스.

### Transfer Family / DataSync

- **Transfer Family** — **FTP·FTPS·SFTP** 프로토콜로 S3·EFS에 파일 전송하는 관리형 서비스. 엔드포인트 시간당 + 전송량 과금. 기존 인증(AD·LDAP·Okta·Cognito)과 통합. "기존 FTP 클라이언트로 S3에 올려야 한다" 시나리오의 답. (FTP는 VPC 안에서만.)
- **DataSync** — 대량 데이터를 **온라인으로 동기화**. 온프레미스/타 클라우드 → AWS(에이전트 필요), AWS → AWS(에이전트 불필요). S3(모든 클래스)·EFS·FSx로 동기화. **시간·일·주 단위 스케줄**, **파일 권한·메타데이터 보존**, 에이전트 1개당 10Gbps. Snow와의 차이: DataSync는 온라인·반복 동기화, Snow는 오프라인 일회성 대량 이전.

### 한눈 비교 (시나리오 매칭)

- 오프라인 페타바이트 이전 → **Snowball**, 현장 연산까지 → **Snowball Edge Compute Optimized**
- 온라인 반복 동기화·메타데이터 보존 → **DataSync**
- Windows 파일 공유(SMB) → **FSx for Windows**, HPC/ML(S3 연동) → **FSx for Lustre**, NFS+SMB+iSCSI 멀티프로토콜 → **FSx for NetApp ONTAP**
- 온프레미스에서 S3를 파일로 → **S3 File Gateway**, 블록(iSCSI) → **Volume Gateway**, 테이프 백업 → **Tape Gateway**
- FTP/SFTP로 S3·EFS 접근 → **Transfer Family**

## 운영 관점 (CloudOps) #cloudops

![[AWS Certified CloudOps Engineer Associate Slides v41.pdf#page=295]]

운영 강의는 이 단원에서 **FSx와 Storage Gateway만** 다루고(Snow·Transfer·DataSync는 여기 없음), SAA와 겹치는 "무엇을 고르나"는 위 설계 관점으로 갈음한다. 운영 시험이 새로 묻는 건 **고른 다음의 일** — FSx의 가용성 구성, Storage Gateway VM을 유지보수로 재부팅하는 순서, 활성화가 실패할 때 점검할 곳, 캐시가 잘 듣는지 보는 지표다.

### FSx for Windows — 가용성 구성 (Single-AZ vs Multi-AZ)

- **Single-AZ**: 한 AZ 안에서만 자동 복제. 세대가 둘 — **Single-AZ 1**(SSD), **Single-AZ 2**(SSD·HDD).
- **Multi-AZ**: AZ 사이를 **동기 복제**하고, **다른 AZ에 standby 파일 서버**를 둬 장애 시 **자동 failover**. 고가용성이 필요하면 Multi-AZ.

### Storage Gateway 운영 — 재부팅 순서가 종류마다 다르다

- **File Gateway는 POSIX 호환**(Linux 파일 시스템). 소유자·권한·타임스탬프 같은 **POSIX 메타데이터를 S3 객체 메타데이터에 저장**한다.
- **VM 유지보수 재부팅(시험 포인트)**: 게이트웨이 종류마다 절차가 다르다.
  - **File Gateway**: 그냥 **Storage Gateway VM을 재시작**하면 된다.
  - **Volume·Tape Gateway**: 순서를 지켜야 한다 — **① Storage Gateway 서비스 중지 → ② VM 재부팅 → ③ 서비스 시작**(콘솔·VM 로컬 콘솔·API 중 하나로). 바로 재부팅하면 안 된다.

### Storage Gateway 활성화 트러블슈팅

게이트웨이를 AWS에 등록하려면 **Activation Key**가 필요하다. 얻는 방법 둘 — **VM CLI**, 또는 **게이트웨이 VM에 포트 80 웹 요청**(`curl 'vm_ip/?activationRegion=...&no_redirect'`).

- **활성화 실패하면**: ① 게이트웨이 VM의 **포트 80이 열려 있는지**, ② VM **시간이 정확하고 NTP 서버와 자동 동기화**되는지 확인. (시간이 틀어지면 활성화가 깨진다.)

### Volume Gateway — 캐시 효율 모니터링

Cached mode는 **최근 데이터만 로컬에 두고** 나머지는 S3에서 당겨온다. 캐시가 잘 듣는지 CloudWatch로 본다.

- **`CacheHitPercent`**: 캐시에서 바로 처리된 비율 — **높을수록 좋다**.
- **`CachePercentUsed`**: 캐시 사용률 — **너무 높으면 안 된다**(꽉 차면 cache miss가 늘어 S3 왕복이 잦아짐).
- 캐시가 부족하면 **더 큰 캐시 디스크**로 — 기존 cached volume을 **더 큰 크기로 클론**한 뒤 그 디스크를 cached volume으로 지정.

## 시험 함정

- 네트워크 전송이 일주일 넘게 걸리면 Snowball. 온라인 반복 동기화는 DataSync. #exam/trap/storage-extras
- Snowball은 Glacier로 직접 못 넣는다. S3 거쳐 라이프사이클로 이동. #exam/trap/storage-extras
- FSx for Lustre는 HPC/ML + S3 연동. Scratch(임시·복제 안 함) vs Persistent(복제·장기). #exam/trap/storage-extras
- FSx for Windows는 SMB지만 Linux EC2에도 마운트된다. 멀티프로토콜(NFS+SMB+iSCSI)은 NetApp ONTAP. #exam/trap/storage-extras
- 온프레미스에서 S3를 파일로 노출 → S3 File Gateway, 블록(iSCSI) → Volume Gateway, 가상 테이프 → Tape Gateway. #exam/trap/storage-extras
- FTP/SFTP로 S3·EFS 접근 요구 → Transfer Family. #exam/trap/storage-extras
- DataSync는 파일 권한·메타데이터를 보존한다(NFS POSIX·SMB). #exam/trap/storage-extras
- FSx for Windows 고가용성 → **Multi-AZ**(동기 복제 + 다른 AZ standby 자동 failover). Single-AZ는 한 AZ 내 복제만 #exam/trap/storage-extras
- Storage Gateway VM 재부팅: **File Gateway는 그냥 재시작**, **Volume·Tape Gateway는 서비스 중지→재부팅→서비스 시작** 순서 #exam/trap/storage-extras
- Storage Gateway 활성화 실패 → **포트 80 열림**·**NTP 시간 동기화** 확인 #exam/trap/storage-extras
- Volume Gateway 캐시 효율 → **CacheHitPercent 높게·CachePercentUsed 너무 높지 않게**. 부족하면 더 큰 캐시 디스크로 클론 #exam/trap/storage-extras
