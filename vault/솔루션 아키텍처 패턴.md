# 솔루션 아키텍처 패턴

> 사례 중심 설계 연습 — WhatIsTheTime, MyClothes, TODO 앱 등 점진적 아키텍처 진화.

## 개요

새 서비스를 배우는 단원이 아니라, 앞서 본 조각들([[EC2]]·[[ELB & Auto Scaling]]·[[RDS & Aurora & ElastiCache]]·[[Route 53]]·[[EBS & EFS]])을 하나의 웹 서비스로 조립하는 연습이다. 작게 시작한 앱이 트래픽이 늘면서 어떤 문제에 부딪히고, 그때마다 무엇을 더해 푸는지를 단계별로 따라간다. SAA 시험의 시나리오 문제가 정확히 이 사고 흐름("이 요구사항이면 뭘 추가해야 하나")을 묻기 때문에, 사례별로 **문제 → 추가한 조각 → 이유**를 기억하는 게 목표다.

세 가지 사례로 진행한다.

- **WhatIsTheTime.com** — DB가 필요 없는 stateless 앱. 확장(scaling)과 가용성 문제를 푼다.
- **MyClothes.com** — 장바구니가 있는 stateful 앱. 세션 상태를 어디에 둘지 푼다.
- **MyWordPress.com** — 이미지 업로드 + MySQL이 있는 앱. 공유 저장소와 DB 확장을 푼다.

### 사례 1: WhatIsTheTime.com — Stateless 앱의 확장과 가용성

현재 시간만 알려주는 앱. DB가 필요 없고, 처음엔 다운타임을 감수하지만 결국 무중단으로 수직·수평 확장하고 싶다. 진화 순서:

1. **EC2 1대 + Elastic IP** — 가장 단순. 고정 public IP 하나로 접속.
2. **수직 확장(Scale Up)**: 인스턴스 타입을 키움(T2 → M5). **업그레이드 중 다운타임**이 생긴다.
3. **수평 확장(Scale Out)**: 인스턴스를 여러 대로. 이제 IP가 여러 개라 **Route 53**으로 묶는다. 단, 인스턴스에 직접 거는 A 레코드는 TTL 때문에 인스턴스가 사라져도 한동안 옛 IP가 캐싱되는 문제가 있다.
4. **ELB 추가**: 앞단에 로드 밸런서를 두고 **Health Check**로 죽은 인스턴스를 빼낸다. 인스턴스는 private으로 숨기고, 보안 그룹은 **ELB에서 오는 트래픽만** 받게 제한. Route 53은 ELB를 가리키는 **Alias 레코드**로 바꾼다.
5. **Auto Scaling Group(ASG)**: 부하에 따라 인스턴스 수를 자동 조절.
6. **Multi-AZ**: ASG를 여러 AZ에 펼쳐 한 AZ가 죽어도 견디게.
7. **비용 최적화**: 항상 떠 있는 최소 용량(minimum capacity)은 **Reserved Instances**로 잡아 비용을 줄인다.

### 사례 2: MyClothes.com — Stateful 앱의 세션 보관

장바구니가 있고 동시 사용자가 수백 명. 수평 확장은 유지하되 앱은 최대한 stateless로 만들고, **사용자가 장바구니를 잃지 않아야** 한다. 핵심은 "여러 인스턴스에 요청이 분산될 때 세션 상태를 어디에 두느냐"다.

| 방법 | 어떻게 | 한계 / 시험 포인트 |
| --- | --- | --- |
| **ELB Stickiness(세션 고정)** | 같은 사용자를 늘 같은 인스턴스로 보냄 | 그 인스턴스가 죽으면 세션 유실. 부하가 한쪽에 쏠림 |
| **사용자 쿠키에 담기** | 장바구니 내용을 클라이언트 쿠키로 들고 다님 → 앱은 stateless | 요청이 무거워짐, **쿠키 변조 위험(검증 필수)**, **쿠키 4KB 미만** 제한 |
| **서버 세션(ElastiCache)** | 쿠키엔 session_id만, 실제 세션 데이터는 [[RDS & Aurora & ElastiCache\|ElastiCache]]에 저장 | 가장 권장. **DynamoDB도 대안** |

- 사용자 정보(주소·이름 등 영속 데이터)는 **RDS**에 저장한다(세션과 구분).
- 읽기 부하가 크면 **RDS Read Replica**로 읽기를 분산하고, RDS에서 읽은 데이터를 **ElastiCache로 캐싱(Lazy Loading)** 해 DB 부하를 더 던다.
- 가용성: ElastiCache와 RDS 모두 **Multi-AZ**로.
- 보안: 보안 그룹이 **서로를 참조**하게 한다(ELB→EC2, EC2→ElastiCache, EC2→RDS). IP/CIDR이 아니라 보안 그룹 ID로 여는 게 핵심.

### 사례 3: MyWordPress.com — 공유 저장소와 DB 확장

이미지 업로드를 모든 인스턴스가 똑같이 보여줘야 하고, 블로그 글·사용자 데이터는 MySQL에 둔다.

- **DB**: [[RDS & Aurora & ElastiCache\|Aurora MySQL]]로 Multi-AZ + Read Replica를 쉽게 구성.
- **이미지 저장 — EBS vs EFS (시험 단골 비교)**:

| | EBS | EFS |
| --- | --- | --- |
| 성격 | 한 AZ에 묶인 블록 스토리지 | 여러 AZ에서 공유하는 네트워크 파일시스템 |
| 적합 | **단일 인스턴스** 앱 | **여러 인스턴스가 같은 파일 공유**(분산 앱) |
| 다중 AZ | 인스턴스마다 따로(공유 안 됨) | AZ마다 ENI(마운트 타깃)로 같은 파일시스템 공유 |

→ WordPress처럼 여러 인스턴스가 같은 업로드 이미지를 봐야 하면 **EFS**가 답.

### 빠른 인스턴스 기동 (Instantiating quickly)

풀 스택을 새로 띄울 때 설치·설정 시간을 줄이는 방법.

- **EC2**: ① **Golden AMI**(앱·OS 의존성을 미리 설치해 이미지로 구움) ② **User Data 부트스트랩**(부팅 시 동적 설정) ③ **하이브리드**(둘을 섞음, Elastic Beanstalk 방식).
- **RDS**: 스냅샷에서 복원하면 스키마·데이터가 이미 준비된 상태로 뜬다.
- **EBS**: 스냅샷에서 복원하면 포맷·데이터가 된 디스크로 뜬다.

### 전형적인 3계층 구조

- **Public Subnet**: [[Route 53]] + ELB
- **Private Subnet**: ASG로 묶인 EC2 인스턴스(앱 계층)
- **Data Subnet**: ElastiCache(세션·캐시) + RDS(영속 데이터)

### Elastic Beanstalk (여기선 큰 그림만)

위 3계층 구조는 대부분의 웹 앱이 똑같이 반복한다. 개발자는 인프라 관리 말고 **코드만 돌리고 싶다** — 이걸 대신해 주는 관리형 서비스가 Elastic Beanstalk다. EC2·ASG·ELB·RDS를 자동으로 깔아주고, 개발자는 앱 코드만 책임진다. Beanstalk 자체는 무료고 그 아래 뜨는 인스턴스 비용만 낸다. 배포 모드는 **Single Instance(개발용)**와 **High Availability with Load Balancer(운영용)**로 나뉜다. 자세한 구성·배포 정책은 [[Elastic Beanstalk]] 노트에서(3단계 DVA).

## 서버리스 아키텍처 패턴 (SAA 전용) #saa

위 사례들이 EC2 기반이었다면, 같은 문제를 **서버 관리 없이** 푸는 방식. 시험은 두 접근을 같은 시나리오로 비교한다.

### 사례 4: MyTodoList — 서버리스 REST API

모바일 앱. HTTPS REST API, 사용자가 자기 S3 폴더에 직접 접근, 관리형 인증, 읽기가 많고 높은 처리량.

- **REST API 계층**: [[API Gateway]] + [[Lambda]] + [[DynamoDB]]. API Gateway가 받아 Lambda를 호출하고 Lambda가 DynamoDB를 조회.
- **인증**: [[Cognito]]로 사용자를 인증하고 API Gateway가 그 토큰을 검증.
- **S3 직접 접근**: Cognito가 **임시 자격증명**을 발급해 사용자가 제한된 정책으로 자기 S3 폴더에 직접 읽고 쓴다. 이 패턴은 DynamoDB·Lambda에도 적용 가능.
- **읽기 많음 → 캐싱**: DynamoDB 앞에 **DAX**(DynamoDB 전용 캐시)를 둬 읽기를 캐싱. 추가로 **API Gateway 응답 캐싱**으로 REST 요청 자체를 캐시.

### 사례 5: MyBlog.com — 서버리스 + 글로벌 + 이벤트 처리

글로벌 확장, 읽기 많고 쓰기 적음, 정적 파일 + 동적 REST API, 신규 가입자 환영 메일, 업로드 사진 썸네일.

- **정적 콘텐츠 글로벌 전송**: [[S3]] + [[CloudFront & Global Accelerator|CloudFront]]. S3는 **OAC(Origin Access Control)**로 잠가 CloudFront 경유만 허용(버킷 정책으로 CloudFront만 인가).
- **동적 API**: API Gateway + Lambda + DynamoDB. 공개 API라 Cognito는 불필요.
- **글로벌 데이터**: **DynamoDB Global Tables**로 여러 리전에 데이터 복제(또는 Aurora Global Database).
- **환영 이메일**: **DynamoDB Streams**가 신규 항목 변경을 잡아 Lambda를 트리거 → Lambda가 IAM 역할로 **SES**를 호출해 메일 발송.
- **썸네일 생성**: 사진을 S3에 업로드(Transfer Acceleration) → **S3 이벤트가 Lambda를 트리거** → 썸네일을 다른 S3에 저장(옵션으로 SQS·SNS 알림).

### Micro Services / 기존 앱 비용 절감

- **마이크로서비스**: 서비스끼리 REST로 직접 통신. **동기 패턴**은 API Gateway·Load Balancer, **비동기 패턴**은 SQS·Kinesis·SNS·S3 Lambda 트리거. 서버리스(API Gateway·Lambda)를 쓰면 자동 확장·사용량 과금·환경 복제가 쉬워 마이크로서비스의 부담을 던다.
- **Software updates offloading**: EC2에서 소프트웨어 업데이트 파일(정적·불변)을 배포하느라 트래픽 비용이 큰 경우, **아키텍처를 바꾸지 않고 앞에 CloudFront만 추가**한다. 엣지에서 캐싱되어 ASG가 덜 확장되고 EC2·네트워크 비용이 크게 준다. 기존 앱을 싸고 확장성 있게 만드는 손쉬운 방법.

## More Solutions Architecture (SAA 전용) #saa

흩어진 이벤트·통합·보안 패턴 모음. 시험에 시나리오로 자주 나온다.

### Lambda + SNS + SQS 통합과 Fan-Out

- **SQS + Lambda**: Lambda가 큐를 polling, 실패 시 재시도, 처리 못 한 메시지는 **DLQ**로. SQS **FIFO** + Lambda는 순서 보장을 위해 blocking 방식.
- **SNS + Lambda**: SNS가 Lambda를 비동기 호출, 재시도하다 실패하면 DLQ(SQS)로.
- **Fan-Out 패턴**: 같은 메시지를 여러 SQS에 넣어야 할 때, SDK로 큐마다 PUT 하면(여러 번 호출, 실패 위험) 비효율적이다. 대신 **SNS 하나에 PUT → 여러 SQS가 구독(subscribe)**하게 한다. 한 번의 발행으로 모든 큐에 전달.

### S3 Event Notifications

`S3:ObjectCreated`·`ObjectRemoved`·`ObjectRestore`·`Replication` 등 이벤트를 **SNS·SQS·Lambda**로 보낸다. 객체 이름 필터(`*.jpg`) 가능. 보통 수 초 내 전달(가끔 1분 이상). **EventBridge로 보내면** JSON 규칙으로 고급 필터(메타데이터·크기·이름), 18개 이상 대상(Step Functions·Kinesis 등), archive·replay·신뢰성 전달이 가능하다.

### 그 밖의 패턴

- **API Gateway 서비스 통합**: Lambda 없이 API Gateway가 AWS 서비스에 직접 연결. 예: 클라이언트 → API Gateway → Kinesis Data Streams → Firehose → S3(.json 저장).
- **Caching 전략**: 요청 경로의 여러 지점에서 캐싱한다 — CloudFront(엣지, 정적·S3), API Gateway(응답 캐시), 앱 계층의 ElastiCache(Redis·Memcached)·DAX. 캐싱·TTL·네트워크·연산·비용·지연을 따져 어디서 캐시할지 정한다.
- **HPC(고성능 컴퓨팅)**: 클라우드는 짧은 시간에 대량 자원을 띄워 HPC에 적합. 관련 서비스 묶음 —
  - 데이터 이전: Direct Connect, Snowball/Snowmobile, DataSync.
  - 컴퓨팅·네트워킹: EC2(CPU/GPU 최적화, Spot), **Placement Group Cluster**(같은 랙·AZ, 저지연 10Gbps), **Enhanced Networking(SR-IOV)** — ENA(최대 100Gbps)/Intel 82599(레거시), **EFA**(HPC용, Linux 전용, MPI 기반, OS를 우회해 노드 간 저지연 통신, tightly coupled 워크로드).
  - 스토리지: EBS(io2 Block Express 최대 256,000 IOPS)·Instance Store, S3·EFS·**FSx for Lustre**(HPC 분산 파일시스템).
  - 자동화: **AWS Batch**(멀티노드 병렬 작업), **AWS ParallelCluster**(오픈소스 HPC 클러스터 배포, EFA 활성화 가능).

### 특정 IP 차단 — 어느 계층에서? (단골 함정)

- **EC2가 퍼블릭 IP**면: **NACL**로 차단(SG는 deny가 없음).
- **앞에 ALB**가 있으면: ALB가 연결을 종료(connection termination)해 EC2는 ALB IP만 본다. 그래서 EC2 레벨이 아니라 **ALB 앞 서브넷의 NACL**이나 **ALB에 WAF**(IP 필터링)로 막는다.
- **앞에 NLB**면: NLB엔 SG가 없으므로 **NACL**로 EC2를 보호.
- **앞에 CloudFront**가 있으면: NACL은 CloudFront의 퍼블릭 IP만 보게 되어 **소용없다**. 이때는 **CloudFront의 Geo Restriction + WAF의 IP 필터링**으로 막는다.

### 고가용성 단일 EC2 만들기

한 대만 떠 있어야 하지만 죽으면 자동 복구돼야 하는 경우.

- 기본형: Elastic IP를 단일 EC2에 붙이고, CloudWatch Event/Alarm이 장애를 감지하면 Lambda가 대기 인스턴스를 켜고 EIP를 옮겨 붙인다.
- **ASG로 더 간단히**: ASG를 **min 1 / max 1 / desired 1, 2개 이상 AZ**로 설정. 인스턴스가 죽으면 다른 AZ에 새로 띄우고, **User Data로 Elastic IP를 자기에게 붙인다**(EIP attach API 호출용 instance role 필요).
- **상태가 있으면 ASG + EBS**: ASG **Terminate 라이프사이클 훅**에서 EBS 스냅샷을 뜨고, **Launch 훅**에서 그 스냅샷으로 볼륨을 만들어 새 인스턴스에 붙여 데이터를 잇는다.

## 시험 함정

- 여러 인스턴스가 **같은 파일 공유** 필요 → EBS 아니라 **EFS** #exam/trap/architecture
- 세션 상태를 stateless하게 외부 보관 → **ElastiCache**(또는 DynamoDB), RDS는 영속 사용자 데이터용 #exam/trap/architecture
- 읽기 부하 분산은 **RDS Read Replica**, 가용성(DR)은 **Multi-AZ** — 둘은 목적이 다름 #exam/trap/architecture
- 계층 간 접근 제어는 CIDR이 아니라 **보안 그룹이 서로를 참조** #exam/trap/architecture
- Route 53으로 ELB를 가리킬 땐 **Alias**(루트 도메인 가능, 무료, TTL 자동) #exam/trap/architecture
- 쿠키 보관 방식은 **4KB 미만 + 변조 검증** 제약 #exam/trap/architecture
- 빠른 기동: 앱 미리 구움 → **Golden AMI**, 부팅 시 설정 → **User Data** #exam/trap/architecture
- 서버리스 REST API = API Gateway + Lambda + DynamoDB. 인증 필요하면 Cognito 추가 #exam/trap/architecture
- 여러 SQS에 같은 메시지 전달 → SNS Fan-Out(SNS에 한 번 PUT, 여러 SQS 구독) #exam/trap/architecture
- S3 업로드 후처리(썸네일 등) → S3 Event Notification → Lambda. 고급 필터·다중 대상이면 EventBridge 경유 #exam/trap/architecture
- DB 변경에 반응(환영 메일 등) → DynamoDB Streams → Lambda → SES #exam/trap/architecture
