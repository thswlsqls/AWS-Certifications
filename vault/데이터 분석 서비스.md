# 데이터 분석 서비스

> 분석 파이프라인 — 어떤 상황에 어떤 서비스인지 매핑이 출제 포인트.

## 개요

데이터를 모으고(수집) → 변환하고(ETL) → 질의하고(분석) → 보여주는(시각화) 파이프라인을 이루는 서비스들이다. 서비스마다 기능을 외우기보다, "이 시나리오엔 무엇?"을 고를 수 있게 경계선을 잡는 게 시험의 핵심이다. 대략의 역할 구분:

- **S3 위 데이터를 SQL로 질의** → Athena(서버리스), 더 빠른 조인·집계가 필요하면 Redshift.
- **데이터 웨어하우스(OLAP·BI)** → Redshift.
- **ETL·데이터 카탈로그** → Glue.
- **하둡·Spark 같은 빅데이터 프레임워크** → EMR.
- **대시보드·시각화** → QuickSight.
- **전체 텍스트·부분 일치 검색** → OpenSearch.
- **데이터 레이크 구축·중앙 권한 관리** → Lake Formation.
- **스트림 처리 프레임워크(Flink)·관리형 Kafka** → Managed Service for Apache Flink, MSK.

### 먼저: 어떤 데이터 저장소를 고를까 (p.516~)

분석 서비스로 넘어가기 전에, 시험이 자주 묻는 "이 워크로드엔 어떤 DB/스토어?"의 큰 갈래를 정리해 둔다. 판단 질문은 읽기/쓰기 비중, 데이터 양과 증가, 지연 요구, 데이터 모델(조인·구조화 여부), 스키마 유연성이다.

- **RDBMS(SQL·OLTP), 조인 필요** → [[RDS & Aurora & ElastiCache\|RDS·Aurora]].
- **키/값·세션·캐시** → ElastiCache, 또는 TTL을 쓰는 [[DynamoDB]].
- **서버리스 NoSQL, 빠르게 바뀌는 스키마** → [[DynamoDB]].
- **큰 객체 저장** → [[S3]], 아카이브 → Glacier.
- **데이터 웨어하우스(SQL 분석·BI, OLAP)** → Redshift, Athena, EMR.
- **전체 텍스트 검색** → OpenSearch.
- **그래프(관계 데이터)** → Neptune.
- **원장(변경 불가 이력)** → QLDB. **시계열** → Timestream.

### Amazon Athena — S3 위 서버리스 SQL

S3에 있는 파일을 옮기지 않고 표준 SQL로 바로 질의하는 서버리스 서비스(엔진은 Presto). CSV·JSON·ORC·Avro·Parquet 지원. **스캔한 데이터 1TB당 약 $5** 과금이라, 비용은 "얼마나 적게 스캔하느냐"로 결정된다. QuickSight와 묶어 리포트·대시보드를 만든다.

- **시험 신호**: "S3 데이터를 서버리스 SQL로 분석" → 무조건 Athena. VPC Flow Logs·ELB 로그·CloudTrail 로그 분석도 단골 예시.
- **성능·비용 최적화** (스캔량 줄이기):
  - **컬럼형 포맷(Parquet·ORC)** 사용 → 필요한 열만 읽음. CSV·JSON을 Parquet로 바꿀 땐 **Glue**로 변환.
  - **압축**(gzip·snappy 등)으로 읽는 양 축소.
  - S3에서 **파티셔닝**(`.../year=1991/month=1/...` 식 경로)으로 가상 컬럼 단위 질의.
  - 작은 파일을 모아 **큰 파일(>128MB)**로 — 파일마다 드는 오버헤드 감소.
- **Athena Federated Query**: S3뿐 아니라 RDS·DynamoDB·DocumentDB·ElastiCache·온프레미스 DB 등 여러 소스를 한 SQL로 질의. 소스별 **Lambda 데이터 소스 커넥터**를 두고, 결과는 S3에 저장.

### Amazon Redshift — 데이터 웨어하우스(OLAP)

PostgreSQL 기반이지만 **OLTP가 아니라 OLAP**(분석·웨어하우징)용. 다른 웨어하우스보다 10배 빠르다고 광고하며 PB급까지 확장. **행이 아니라 컬럼형 저장 + 병렬 질의 엔진**이라 대량 집계에 강하다. SQL 인터페이스를 제공하고 QuickSight·Tableau 같은 BI 도구가 붙는다.

- **vs Athena**: 인덱스 덕분에 조인·집계가 더 빠르다. 정리하면 — **가끔 하는 임시 질의·서버리스**면 Athena, **반복되는 복잡한 분석을 빠르게**면 Redshift.
- **두 가지 모드**: Provisioned 클러스터(인스턴스 타입 미리 선택, 예약 인스턴스로 비용 절감) vs Serverless 클러스터.
- **클러스터 구조**: **Leader Node**(질의 계획·결과 취합) + **Compute Node**(실제 질의 수행). 노드 수로 확장.
- **스냅샷·DR**: 일부 클러스터는 Multi-AZ 지원. 스냅샷은 내부적으로 S3에 저장되는 시점 백업이고 **증분**(바뀐 부분만)이며 **새 클러스터로 복원**한다. 자동(8시간마다 / 5GB마다 / 스케줄, 보존 1~35일)과 수동(지울 때까지 보존). **다른 리전으로 스냅샷 자동 복사** 설정 가능 → 리전 간 DR.
- **데이터 적재**: 큰 단위 삽입이 훨씬 빠르다. 경로는 Kinesis Data Firehose, **S3에서 `COPY` 명령**, EC2의 JDBC(배치 권장). S3↔Redshift 트래픽을 VPC 안으로 돌리려면 **Enhanced VPC Routing**.
- **Redshift Spectrum**: S3 데이터를 **적재하지 않고** 바로 질의. 단, 질의를 시작하려면 **Redshift 클러스터가 떠 있어야** 한다(질의가 수천 개의 Spectrum 노드로 퍼짐). "이미 Redshift를 쓰는데 S3의 추가 데이터까지 함께 질의" 시나리오의 답.

### Amazon OpenSearch — 검색

옛 Amazon ElasticSearch의 후속. **모든 필드를, 부분 일치까지** 검색할 수 있다(DynamoDB는 기본키·인덱스로만 질의 가능). 보통 다른 DB를 **보조**하는 검색 계층으로 쓴다. 관리형/서버리스 모드, 기본적으로 SQL은 안 되고(플러그인으로 가능), Kinesis Data Firehose·IoT·CloudWatch Logs에서 수집, Cognito·IAM·KMS·TLS로 보안, 시각화용 OpenSearch Dashboards 포함.

- **DynamoDB + OpenSearch 패턴**: 항목은 DynamoDB에서 가져오고(retrieve), 검색은 OpenSearch로(search). 동기화는 DynamoDB Streams → Lambda → OpenSearch.
- **CloudWatch Logs → OpenSearch**: Subscription Filter 뒤에 Lambda(실시간) 또는 Kinesis Data Firehose(준실시간).

### Amazon EMR — 하둡·Spark 빅데이터

"Elastic MapReduce". 수백 대 EC2로 **하둡 클러스터**를 띄워 대용량 데이터를 처리. Apache Spark·HBase·Presto·Flink가 번들로 들어 있고, 프로비저닝·설정을 EMR이 알아서 한다. 오토스케일링 + **Spot 인스턴스** 연동으로 비용 절감.

- **노드 종류**: **Master**(클러스터 관리·조율, 장기 실행), **Core**(작업 수행 + 데이터 저장, 장기 실행), **Task**(선택, 작업만 수행 — **주로 Spot**으로 띄워 비용 절감).
- **구매 옵션**: On-Demand(안정), Reserved(최소 1년, 비용 절감, EMR이 있으면 자동 사용), Spot(저렴·종료 가능). 클러스터는 장기 실행 또는 **transient(일회성)**으로 운영.

### Amazon QuickSight — BI·대시보드

서버리스 ML 기반 BI 서비스로 대화형 대시보드를 만든다. **세션 단위 과금**, 임베드 가능, 자동 확장. RDS·Aurora·Athena·Redshift·S3 등과 통합.

- **SPICE**: 데이터를 QuickSight로 가져오면(import) 쓰는 인메모리 연산 엔진. 빠른 분석이 필요할 때.
- **Column-Level Security(CLS)**: Enterprise 에디션에서 열 단위 접근 제어.
- **사용자·그룹은 QuickSight 안에만 존재하고 IAM이 아니다.** (그룹은 Enterprise 전용.)
- **대시보드 = 분석(analysis)의 읽기 전용 스냅샷**으로 공유 가능. 공유하려면 먼저 게시(publish)해야 하고, **대시보드를 보는 사람은 그 밑의 원본 데이터도 볼 수 있다**(권한 설계 주의).

### AWS Glue — ETL·데이터 카탈로그

관리형 **ETL(추출·변환·적재)** 서비스, 완전 서버리스. 분석에 쓸 데이터를 준비·변환한다. 대표 용례가 **CSV → Parquet 변환**(S3 PUT 이벤트 → Lambda가 Glue Job 트리거 → Parquet로 변환 → Athena로 분석).

- **Glue Data Catalog**: Glue Data Crawler가 S3·RDS·DynamoDB·JDBC를 훑어 메타데이터(테이블 정의)를 기록. 이 카탈로그를 **Athena·Redshift Spectrum·EMR**이 공유해 데이터 검색에 쓴다.
- 알아둘 기능: **Job Bookmarks**(이미 처리한 옛 데이터 재처리 방지), **DataBrew**(코드 없이 데이터 정제·정규화), **Studio**(ETL 잡 GUI), **Streaming ETL**(Spark Structured Streaming 기반, Kinesis Data Streams·Kafka·MSK 호환).

### AWS Lake Formation — 데이터 레이크

여러 소스의 데이터를 분석용으로 한곳에 모으는 **데이터 레이크**를 며칠 만에 구축하게 해 주는 관리형 서비스. **Glue 위에 만들어졌다.** 수집·정제·이동·카탈로깅 같은 복잡한 수작업을 자동화하고, ML Transforms로 중복 제거. S3·RDS·관계형/NoSQL DB용 소스 블루프린트 제공.

- **시험 신호**: **행·열 단위 세분화 접근 제어(fine-grained access control)를 한곳에서** 관리하고 싶다 → Lake Formation. (밑단 Athena·Redshift·EMR·QuickSight로 데이터가 흘러가도 권한은 Lake Formation에서 중앙 관리.)

### 스트림 분석: Flink와 MSK

- **Amazon Managed Service for Apache Flink** (옛 Kinesis Data Analytics for Apache Flink): Flink(Java·Scala·SQL)로 **데이터 스트림을 처리**하는 프레임워크를 관리형 클러스터에서 실행. 입력은 **Kinesis Data Streams·MSK**. **중요한 함정: Firehose에서는 못 읽는다.**
- **Amazon MSK** (Managed Streaming for Apache Kafka): Kinesis의 대안인 **관리형 Kafka**. 브로커·Zookeeper를 AWS가 관리, VPC 안에 Multi-AZ(최대 3)로 배치, 데이터를 **EBS에 원하는 만큼 오래** 보관. **MSK Serverless**도 있음.
- **Kinesis Data Streams vs MSK**: 메시지 크기 한도가 KDS는 **1MB**, MSK는 기본 1MB지만 **더 크게(예: 10MB) 설정 가능**. KDS는 Shard(분할·병합 가능), MSK는 Topic/Partition(**파티션 추가만 가능, 줄이기 불가**). 암호화는 KDS가 전송 중 TLS 고정, MSK는 **PLAINTEXT 또는 TLS** 선택.

### 빅데이터 수집 파이프라인 (조합 예시)

서버리스로 실시간 수집→변환→SQL 질의→리포트까지 잇는 대표 구성:
**Kinesis Data Streams(실시간 수집)** → **Kinesis Data Firehose(1분마다 S3로 전달, Lambda로 변환)** → **S3 수집 버킷** → (선택: S3 이벤트 → SQS → Lambda) → **Athena(서버리스 SQL)** → **S3 리포트 버킷** → **QuickSight·Redshift(대시보드)**.

## 시험 함정

- S3 데이터를 서버리스 SQL로 분석 → Athena. 반복되는 복잡한 조인·집계를 빠르게 → Redshift. #exam/trap/analytics
- Athena 비용은 스캔량으로 결정된다. Parquet/ORC(컬럼형)·압축·파티셔닝·큰 파일로 스캔량을 줄인다. #exam/trap/analytics
- 여러 데이터 소스(RDS·DynamoDB·온프레미스)를 한 SQL로 → Athena Federated Query(Lambda 커넥터). #exam/trap/analytics
- Redshift는 OLAP(분석)용, OLTP 아님. 컬럼형 저장 + 병렬 질의. #exam/trap/analytics
- Redshift Spectrum은 S3를 적재 없이 질의하지만 **클러스터가 떠 있어야** 한다. #exam/trap/analytics
- Redshift 스냅샷은 증분이고 새 클러스터로 복원, 다른 리전으로 자동 복사 가능(리전 DR). #exam/trap/analytics
- 부분 일치·전체 텍스트 검색 → OpenSearch. DynamoDB는 기본키·인덱스로만 질의. #exam/trap/analytics
- EMR Task 노드는 보통 Spot으로 띄워 비용 절감. Master·Core는 장기 실행. #exam/trap/analytics
- QuickSight 사용자·그룹은 IAM이 아니라 QuickSight 안에만 있다. 대시보드를 보면 원본 데이터도 보인다. #exam/trap/analytics
- CSV→Parquet 변환·데이터 카탈로그 → Glue. 옛 데이터 재처리 방지 → Glue Job Bookmarks. #exam/trap/analytics
- 행·열 단위 중앙 접근 제어 데이터 레이크 → Lake Formation(Glue 위에 구축). #exam/trap/analytics
- Apache Flink(Managed Service for Apache Flink)는 Firehose에서 못 읽는다. 입력은 Kinesis Data Streams·MSK. #exam/trap/analytics
- KDS는 1MB 고정·Shard, MSK는 메시지 크게 설정 가능·Partition(추가만 가능)·PLAINTEXT도 가능. #exam/trap/analytics
